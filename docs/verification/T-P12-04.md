## API additive del guard atomico

AtomicReportFile::writer rimane invariata. writer_send espone il File già
owned come Write+Send: è una proprietà reale del File, senza unsafe, thread o
wrapper che dichiari Send fittiziamente. Soddisfa il bound del backend XLSX.
open_reader esegue flush verificato e apre un handle indipendente del .part
owned dall'inizio. Il file non è pubblicato e il path non è reso mutabile al
chiamante. OutputOperation::Read distingue la nuova causa IO, preservata come
ReportError::Output. I confini sono gli stessi del guard esistente: directory
controllata, nessuna nuova pretesa di protezione da mutazioni ostili/TOCTOU.

## ErrorSpool — spiegazione di ogni operazione

Enum privata dell'adapter con Report(AtomicReportFile) e Temporary(NamedTempFile).
create usa il guard esistente se è indicata una destinazione JSONL, altrimenti
NamedTempFile::new nella temp di sistema. Nessun file fittizio o path predefinito
nel bundle/cwd. Il tempfile usa creazione esclusiva e cleanup RAII.
writer restituisce un'unica interfaccia Write sul file effettivo; JsonlSink
scrive esattamente una volta lo stesso flusso canonico.
reader delega a open_reader oppure flush+NamedTempFile::reopen: nuovo cursore a
zero, identità del tempfile controllata dal crate. Non clona un cursore a EOF.
abort chiude/elimina il file temporaneo o abortisce il guard. complete pubblica
il JSONL secondo ReportCompletion oppure chiude/elimina lo spool temporaneo.
cleanup converte un reale errore di chiusura/rimozione in OutputCleanup, non
ignora l'errore né lo presenta come violazione normativa. Nessun PHI nei log.

## Parsing, percorsi e lifecycle

ValidateArgs è privata del binario: errors diventa Option<PathBuf>, xlsx è una
nuova Option<PathBuf>. --errors/alias --output resta valido; --xlsx seleziona
esplicitamente il workbook, non lo deduce dall'estensione. --errors è richiesto
se manca --xlsx; --summary rimane richiesto. Parsing e ValidationRequest non
leggono file e mantengono scope/mode/opzioni/encoding precedenti.

check_outputs visita tutti i final e .part di errors eventuale, summary e xlsx
prima della creazione dei guard. La stessa risoluzione nativa impedisce
collisioni fra output/part, input e bundle, incluse alias risolvibili. Non
abbassa le protezioni per il nuovo formato.

validate_with_token prepara il service reale e apre lo spool, poi summary e
XLSX guard eventuale. Ogni errore di preparazione abortisce quanto già owned,
mai un .part preesistente non acquisito con create_new. La funzione abort ora
riceve anche lo spool opzionale: tenta tutte le cleanup e conserva primary e
ogni errore secondario in FailedRun. None significa spool già consumato, non
una cleanup saltata o sostituita da un provider finto.

Il servizio valida con JsonlSink sullo spool. finish verifica il flush prima
della rilettura. Logging, summary e human output restano fallibili prima delle
pubblicazioni. Solo se lo stato non è Cancelled e non è truncated, il reader
canonico e il summary effettivo vanno a XlsxReportWriter. CompletedInvalid è
un'analisi regolarmente completata: produce XLSX ed exit 2. CompletedValid con
Partial reference produce XLSX che conserva esplicitamente completezza/audit.

Ordine finale: complete dello spool (pubblicazione JSONL richiesto o rimozione
del temporaneo), complete del summary, complete XLSX per ultimo. Nessuna
operazione fallibile resta dopo il rename del workbook. Quindi un errore di
produzione o pubblicazione precedente non lascia un nuovo XLSX definitivo.
Cancelled/truncated non invocano il writer e i guard complete scartano i part,
conservando eventuali report precedenti. È atomicità per file, non transazione
multi-file: se la pubblicazione di un file successivo fallisce, un JSONL già
pubblicato può essere presente. Questa limitazione preesistente è preservata.
