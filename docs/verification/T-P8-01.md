4.6.7 già nominato dal piano, features minime std/help/usage/error-context,

ramo su Linux GNU/Windows MSVC, lock versionato; nessun crate di test nuovo.

Questa task prepara request, sintassi, directory ed exit code. Il main ora
espone help/parsing e il resolver, poi rifiuta esplicitamente l’esecuzione
validate, assegnata a T-P8-03. Nessun input aperto/report scritto/CompletedValid
simulato: è uno scheletro dichiarato anche nell’help e nel README. Non vengono
introdotti provider o repository fittizi, né una factory completa con parametri
ignorati. I path reference servono qui alla verifica della completezza del bundle;
non dichiarano disponibile ReferenceDataProvider. Le capacità restano quelle
LocalOnly approvate, e il comando non accetta Full o --bom strip.

Exit code da DET §97: valido 0, tecnico 1, invalido normativo 2, cancellato 130.
Quindi i parser error di clap (normalmente 2) sono tradotti a 1, non presentati
come CompletedInvalid. Nessun nuovo simbolo esportato dalla libreria.

## Strutture, funzioni e condizioni

`args::ValidateArgs` possiede request applicativa reale, encoding, directory
bundle e output nativi. `command` usa builder clap: campi stringa obbligatori
non vuoti; path interpretati come PathBuf; --errors ha alias --output;
--encoding utf8 è obbligatorio, unico binding oggi supportato, senza fallback.
Flow/schema-version/trace devono essere espliciti; `parse` mappa i valori nei
newtype pubblici, scope Trace/LocalOnly, StrictSkipRecord, AutoLfOrCrlf e
max_errors None. Il helper `required` usa expect solo sull’invariante del parser
interno dopo successo, non su input esterno non controllato. CLI non compila
schemi, non implementa norme e non deduce encoding dal sistema/BOM.

`exit_code::from_status` è const ed esaustiva, con tre esiti controllati.
VALID deriva da quel mapping, TECHNICAL resta 1. `from_parse_error` distingue
stdout help da errori stderr; non delega a clap l’uscita del processo.

`paths::CliDirs` è la configurazione opzionale esplicita; default significa
nessuna opzione, non una root cwd. `BundleSource::External` conserva entrambe
le root. Embedded verrà introdotto in T-P15-03: nessuna variante fittizia ora.
`EnvProvider` conserva OsString; SystemEnv legge solo i due nomi documentati.
BundleLevel e DirectoryKind rendono tipizzata la diagnosi del livello vincente
e del componente mancante. BundleResolveError distingue coppia incompleta,
path vuoto, oggetto non directory, errore metadata con causa io reale,
exe senza parent e assenza di bundle esterno. Display non rilegge file;
Error::source espone solo l’errore I/O reale. Queste sono diagnosi adapter,
mai path serializzati nei report sanitari.

`directory` rifiuta prima un PathBuf vuoto, poi richiede metadata.is_dir();
fallimenti propagati con causa e componente, senza fallback. `selected_pair`
ha quattro casi: nessuna root = livello assente, un solo componente = errore
incomplete con missing esplicito, entrambe = validazione dei due path e risultato
External. Nessun mix fra livelli: attua fallback a livello bundle di ARCH §39C.2.
Una coppia CLI parziale non si completa con env/exe, e una coppia env parziale
non si completa con exe; questo evita bundle assemblati da origini diverse.

`adjacent` gestisce solo le directory accanto all’exe: directory valida = presente,
NotFound = assente, file o altri errori = errore tecnico. `resolve_bundle_source`
ritorna al primo livello selezionato; `?` impedisce qualsiasi ripiego dopo errore.
Solo senza opzioni/env cerca nel parent esplicito dell’exe; parent assente/vuoto
fallisce. Senza entrambe le directory adiacenti produce NoExternalBundle.
Il resolver controlla directory, non inventa MANIFEST o provider P11; schema
selezionato/versione saranno verificati dal repository durante l’esecuzione.
Non consulta cwd/home, non usa path build-time, non cerca lo schema più recente.

`cli::run` gestisce parsing e stampa degli errori/help con exit code del progetto;
acquisisce current_exe al confine, delega al resolver e in questo step interrompe
con errore tecnico esplicito prima di invocare un servizio. I valori preparati
sono posseduti, non un risultato di validazione. `main` restituisce l’ExitCode
senza exit impliciti clap; il wiring dei sink e dell’esecuzione resta T-P8-03.

## Test e ragioni di correttezza

FakeEnv possiede una mappa, nessuna mutazione dell’ambiente globale. Fixture
crea una directory unica con PID/timestamp/contatore atomico; pair crea due
directory effettive, exe produce un path iniettato e Drop pulisce solo dati
sintetici posseduti. argv prepara opzioni native per un input con spazi;
assert_pair confronta entrambe le root, environment costruisce la porta fittizia
partendo da path effettivi (nessuna conversione UTF-8 lossy).

Otto test binary-unit verificano:
1. mapping completo request, scope, encoding e output; nessun accesso file;
2. help 0, nessuna opzione/flag non supportato/errori sintassi 1; rifiuto encoding
   non supportato e encoding mancante, nessun strip/full silenzioso;
3. alias output e path directory con spazi preservati;
4. mapping esaustivo 0/1/2/130;
5. coppie complete a tutti e tre i livelli, precedenza rigorosa;
6. coppie incomplete CLI/env/exe, senza mix/fallback;
7. root inesistente/vuota/file ed env errata, nessun ripiego;
8. nessuna ricerca in cwd/home e parent exe invalido, nessun Embedded fittizio.

La fixture di directory vuote verifica solo la risoluzione del bundle: non è
un dataset sintetico di produzione. Test a livello processo completi restano
T-P8-06, ma help e no-opzioni sono verificati anche manualmente in questa task.
I primi check durante la scrittura hanno rilevato il file tests.rs ancora da
creare e dead code temporaneo del mapping. Risolti completando i test e usando
la funzione const come fonte unica del codice VALID, senza allow del lint.
Nessun warning soppresso e nessun test di privacy eliminato.
