## Spiegazioni del codice

`signal::cancellation_handler` cattura un clone di CancellationToken e ritorna
una closure FnMut + Send + 'static. Il callback chiama esclusivamente cancel:
operazione atomica idempotente già verificata in P7. Non legge input, non fa
I/O, non rimuove output, non chiama exit e non blocca l'handler con mutex propri.
Cloni dello stesso token condividono il flag; token di run diversi restano isolati.

`signal::install` crea il token e registra una sola volta l'handler nel processo
validate. Restituisce il token solo dopo set_handler riuscito; `?` propaga errori
tecnici di registrazione. Non ignora Ctrl+C quando la piattaforma rifiuta il
setup e non usa un token indipendente dall'handler. Help/version e schema lint
non installano handler perché non passano da command::validate.

`command::validate` esegue install prima di risoluzione bundle, input e output,
poi delega a validate_with_token. Questa separazione consente test portabili del
vero adapter senza registrazioni globali concorrenti nel processo test. La
funzione interna accetta un riferimento al token e lo passa invariato al servizio;
nessun nuovo API libreria, override di RunStatus o finta richiesta cancellata.

Il servizio controlla il token ai checkpoint approvati (prima/durante trace,
finalizzazione prima del summary). Il resto dell'adapter è invariato: JSONL e
summary restano provvisori, HumanReadableSink dichiara CANCELLED/incompletezza,
ReportCompletion usa lo stato del servizio; AtomicReportFile scarta le parti
per Cancelled e il mapping restituisce 130. Il callback non può pubblicare o
rinominare file. Guasti tecnici durante flush/cleanup restano 1, non 130.
Il checkpoint RunCompleted fissa l'esito come già ratificato: un segnale successivo
non trasforma retroattivamente un CompletedValid/Invalid in Cancelled.
Nessuna variazione di EOF, Complete/Incomplete, digest raw o RunStatus.

Un test processo Linux nuovo in cli_validate.rs:
- Prepara input sintetico streaming di 1.048.576 record (7.340.032 byte), apre
  processo CLI con pipe stdout/stderr, attende evento reale run_started. L'handler
  è già installato a quel punto. Invia SIGINT con comando di sistema kill al solo
  PID figlio; se l'invio fallisce, termina e raccoglie il figlio prima del panic.
- Conserva aperto il reader stderr per evitare BrokenPipe spurio e attende il
  processo; stdout ha CANCELLED/incomplete, nessuna frase di conformità, exit
  130, evento run_completed e vecchi report intatti; parti proprie eliminate.
  Nessuna sleep o opzione di test nascosta nell'eseguibile.
- La lunga fixture rende il segnale deterministico rispetto al completamento;
  il test non richiede un numero minimo di record letti prima della cancellazione.

Windows: callback e adapter precancellato eseguono lo stesso comportamento di
cancellazione/atomicità nel runner nativo. GenerateConsoleCtrlEvent reale non
eseguito: richiede controllo della console/process group, non garantito dal
runner; il test SIGINT è esplicitamente Linux. Nessuna equivalenza simulata con
un segnale Windows reale dichiarata. Test regressioni servizio EOF/mid-run/late
cancel e output atomico preesistenti mantenuti ed eseguiti.
