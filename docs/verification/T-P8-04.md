## Contratto e spiegazioni del codice

`args::CliCommand` distingue Validate(Box<ValidateArgs>) e SchemaLint(LintArgs).
Il Box mantiene contenuta la dimensione dell'enum, senza duplicare request o
aggiungere API nella libreria. LintArgs conserva solo schema_root, SchemaKey
ed encoding. Nessun input/report/reference provider fittizio per un'operazione
schema-only. Il builder clap richiede schema lint, root, flow/version e utf8
espliciti; non accetta opzioni validate nel ramo lint. È un affinamento della
sintassi adapter consentito da DET §96, non un nuovo contratto engine.

`parse` si basa sulle invarianti del builder: dopo successo una subcommand è
obbligatoria; nel ramo schema è obbligatoria lint. Solo questo ramo costruisce
LintArgs; validate conserva gli stessi campi/opzioni/policy precedenti. Gli
expect sono esclusivamente invarianti interne dopo parsing tipizzato, non input
esterni senza verifica. Il helper parse_validate nei test precedenti estrae
il payload della variante Validate, mantenendo tutte le vecchie asserzioni.

`cli::run` effettua dispatch esaustivo, preserva il mapping RunStatus per
validate e usa direttamente l'esito lint. Il messaggio tecnico diventa command
failed, corretto per entrambe le operazioni; nessuna diagnosi schema diventa
ValidationError di un paziente e nessuna modifica del servizio.

`command::schema_lint` costruisce repository filesystem reale e SchemaRegistry
con SchemaCompiler/encoding esplicito, poi chiama resolve_with_hash proprio
come ValidationService. Non legge/parsa schemi con un secondo parser e non
riproduce alcun controllo: duplicati JSON, chiavi esatte, formato, fingerprint,
binding encoding, lint fisico e controlli semantici/capability sono gli stessi
del percorso produttivo. Nessuna selezione implicita, nessun fallback.

Tre rami: successo stampa risultato VALID e scope compiler_supported_subset,
exit 0; SchemaResolutionError::Compilation stampa le issue nello stesso ordine
e risultato INVALID con numero issue, exit 2; altri errori tipizzati si propagano
al ramo tecnico, exit 1. Il compiled prodotto non viene forgiato né mutato.
Warning/Error sono presentate senza reinterpretare la severity; il compiler
corrente non produce warning nei percorsi supportati. Non si certifica la
completezza normativa di uno schema, solo la compilabilità attuale.

Ogni issue è un oggetto JSON su una riga stdout con severity, codice compiler,
flow/trace/field, message/source_note. La formattazione JSON effettua escaping
anche di eventuali metadati con newline; non deduce source note assenti. I codici
SchemaIssueCode sono nomi dei variant correnti, separati dai codici normativi
E_* dei ValidationError. Nessuna modifica dei report JSONL/summary di validate.
serde_json::Value ha ordine delle chiavi deterministico nella configurazione
esistente. Ogni scrittura e flush è verificata; un writer fallito ritorna errore
tecnico, non uno schema VALID/INVALID riuscito. Gli errori tecnici restano stderr.
