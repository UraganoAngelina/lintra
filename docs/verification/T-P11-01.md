## Strutture, funzioni e condizioni

DatasetKey esisteva già nel compiled plan con DatasetId/Version, Eq/Hash.
Il modulo dataset lo re-esporta come medesimo tipo: niente doppia identità,
conversione di stringhe o nuovo Ord arbitrario per adattarlo a una collection.
LookupSet è il trait Send+Sync del design, con contains(&[u8]) e key borrow.
Il contratto opera su byte esatti e non effettua trim/case folding/rimozione
zeri. Implementazioni concrete possono usare hash membership; la policy di
normalizzazione sarà dichiarata altrove, mai inferita dal nome di un dataset.
ReferenceDataProvider è il trait Send+Sync con load(key) fallibile che restituisce
Arc<dyn LookupSet>, come previsto. Nessuna apertura per ogni campo nella porta
prepared: il caricamento è un'operazione separata, non una membership bool.

ReferenceDataError è un errore tecnico non_exhaustive. InvalidKey conserva
la chiave invalida, Unavailable la dipendenza assente, KeyMismatch entrambe
le identità, Provider chiave e causa reale Box<dyn Error+Send+Sync>. source()
restituisce la causa originale (non un errore ricostruito da una stringa).
Display è stabile senza valori paziente; i payload rimangono disponibili ai
mapper applicativi futuri. contains=false non è una di queste varianti:
valore fuori dominio e preparazione tecnica restano livelli distinti.
Non sono dichiarati errori di adapter non ancora esistenti o cause fittizie.

PreparedReferenceData ha campi privati: HashMap<DatasetKey,Arc<dyn LookupSet>>
per lookup O(1) atteso e Vec<DatasetKey> nell'ordine della prima dichiarazione.
get restituisce borrow al set già caricato, senza invocare provider; keys espone
l'ordine deterministico, len/is_empty descrivono gli handle effettivi. Non ci
sono setter, Deserialize, constructor pubblico o Default che finga una
preparazione riuscita. Un piano esplicitamente vuoto si prepara senza load.
La struttura non conserva il provider, dunque non offre una strada per riaprire
file durante i field lookup. I set sono Arc reali, non membership simulata.

prepare_reference_data prima verifica tutte le identità: id/version nonempty
e senza whitespace esterno. Un'identità malformata in fondo alla lista fallisce
prima di qualunque side effect del provider. La verifica non riscrive la chiave
né normalizza byte di membership. Poi visita le dipendenze nell'ordine:
chiave esatta già caricata→riusa il set; altrimenti load, confronta key() con
richiesta, inserisce handle e ordine soltanto se identità/versione corrispondono.
Un provider che restituisce un dataset/versione diverso è errore anche quando
i codici contenuti avrebbero coinciso. Non esiste latest/default/upgrade.

Due versioni diverse dello stesso id sono chiavi distinte per questa factory,
come prevede HashMap<DatasetKey,...>; nessun appiattimento per id. L'audit della
run è scope 11-06, non viene costruito ora fingendo di avere la stessa struttura
delle chiavi. L'ordine della HashMap non influenza output o ordini di caricamento.
Duplicati esatti sono caricati una sola volta; non si salta un controllo diverso.
Un Err propaga la causa immediatamente, scarta gli handle locali e non restituisce
un prepared parziale. Le dependency successive non vengono caricate dopo errore.
Il helper non prende né apre input di pazienti; il collegamento che garantisce
l'ordine preflight→parsing nel servizio sarà introdotto solo con 11-06.

mod.rs registra i moduli privati e lib.rs re-esporta soltanto key/trait/context/
factory/errore del contratto pubblico. Nessun accesso ai constructor compiled,
nuova dipendenza Rust o dipendenza inversa verso application/CLI/engine.

## Test

Sei integration test con un set HashSet effettivo e un provider di registrazione
soltanto test: non è l'InMemoryReferenceDataProvider futuro né un default del
runtime. Implementa load sulle mappe di test e registra le richieste in Mutex
per rispettare Send+Sync; la membership confronta i byte reali.
- tre dependency uniche (anche stesso id/versioni diverse), ordine e deduplica;
  mille lookup successivi senza altre load; versione assente senza fallback;
- zeri/spazi/case/NUL/non-UTF-8 esatti, nessuna normalizzazione implicita;
- dataset mancante con chiave e stop prima della dipendenza successiva;
- set restituito con id o versione sbagliati, nessuna accettazione per contenuto;
- identità invalide prima delle load, piano vuoto con zero chiamate;
- errore PermissionDenied del provider con source downcast al vero io::Error.

Tutti i dati sono sintetici. Gli unwrap sono nelle asserzioni di test, non
nella factory o nel trattamento di input esterno. Non si inventano audit,
header, metadati normativi, parser o contenuti ufficiali per soddisfare la firma.
